SMS Builder (CZ/SK)

An assistant that turns a campaign ticket into the finished SMS send script — and catches what a reviewer who reads neither Czech nor Slovak cannot see.

The problem

SMS copy arrives from the client already written, together with its tagging, in a ticket. Turning that into a send script is mechanical but rule-dense: which script you need depends on what sits inside the text — a plain message, a fixed link, a link that comes from the data, a personal salutation. Tracking parameters are derived from naming conventions. And Czech and Slovak carry characters outside the GSM-7 alphabet, which quietly changes how a message is encoded and charged.

What I built

An assistant in IBM Consulting Advantage. You paste the message body and the tagging from the ticket; it works out which script type the text needs, derives the tracking parameters from the naming convention, and returns the finished script. The rules live in a knowledge base I wrote — the assistant is configuration around that document, not magic. It matters because the team includes colleagues who read neither language, so the language-dependent checks are invisible to them.

What surprised me

A large part of the knowledge base ended up describing what the assistant must never produce. A generative tool does not fail here by refusing — it fails by returning a script that looks entirely plausible, uses a variable name that does not exist, and breaks in production. So every wrong answer I hit during testing went back into the document as an explicit counter-example. Writing down the failure modes turned out to be worth more than writing down the happy path.

Where it stands

Presented to a team of fifteen and used by most of it. It is scoped to our team — opening it up more widely needs permissions and rework, and this was a side project outside my scope on the client engagement.

The character problem, in code

Written from scratch for this page — not the tool’s code.

// GSM 03.38 basic alphabet. Anything outside this set forces the whole
// message to UCS-2, where one segment holds 70 characters instead of 160.
const GSM7 =
  "@£$¥èéùìòÇ\nØø\rÅåΔ_ΦΓΛΩΠΨΣΘΞÆæßÉ !\"#¤%&'()*+,-./0123456789:;<=>?" +
  "¡ABCDEFGHIJKLMNOPQRSTUVWXYZÄÖÑÜ§¿abcdefghijklmnopqrstuvwxyzäöñüà";

// Extension characters: each one costs two of the 160.
const GSM7_EXT = "^{}\\[~]|€";

function analyse(text) {
  const chars = [...text];
  const outside = chars.filter(c => !GSM7.includes(c) && !GSM7_EXT.includes(c));

  if (outside.length) {
    const len = chars.length;
    return {
      encoding: "UCS-2",
      length: len,
      segments: len <= 70 ? 1 : Math.ceil(len / 67),
      forcedBy: [...new Set(outside)]
    };
  }

  const len = chars.reduce((n, c) => n + (GSM7_EXT.includes(c) ? 2 : 1), 0);
  return {
    encoding: "GSM-7",
    length: len,
    segments: len <= 160 ? 1 : Math.ceil(len / 153),
    forcedBy: []
  };
}

A 158-character message plus one č is not 159 characters. It is three segments.
